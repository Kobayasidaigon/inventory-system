# 週次在庫管理システム

小売店向けの週次在庫管理システムです。紙で管理した在庫の増減を週単位でまとめて入力できます。

## 機能

- **商品マスター管理**: 商品の登録・編集・削除、画像アップロード対応
- **週次在庫入力**: 紙の記録を週単位でまとめて入力、商品画像表示
- **入庫処理**: 商品が追加されたタイミングで随時入力、商品画像表示
- **在庫状況確認**: 現在庫と発注点の確認、カテゴリフィルター対応
- **発注依頼の確認**: 発注依頼を出してまだ届いていない商品を「発注依頼」タブで一覧、依頼の抜けもここから依頼
- **シフト区切りの確認**: 区切りごとに在庫登録を確定（未確認のLINE通知は現在停止中）
- **履歴管理**: 入出庫履歴の確認と修正、カテゴリ・商品フィルター対応
- **出庫記録**: 誰が何個出したかを出庫のたびに残し、人ごとに集計・CSV 出力。補充が早すぎる商品を知らせる
- **在庫推移グラフ**: 在庫の推移と消費量を 2 枚のグラフで可視化、発注分析機能
- **シフト取得**: ジョブカンから勤務シフトを毎月自動で取り込み
- **CSVエクスポート**: 在庫データ・履歴・発注依頼・出庫記録のExcel出力
- **レスポンシブ対応**: PC・タブレット・スマートフォンに対応
- **マルチテナント**: ユーザーごとに独立したデータベース（オプション）

## セットアップ

### 必要環境
- Node.js (v14以上)
- npm

### インストール手順

1. プロジェクトディレクトリに移動
```bash
cd inventory-system
```

2. 依存パッケージをインストール
```bash
npm install
```

3. サーバーを起動
```bash
npm start
```

開発モード（自動再起動）で起動する場合：
```bash
npm run dev
```

4. ブラウザでアクセス
```
http://localhost:3000
```

## 使い方

### 初回セットアップ（管理者アカウント作成）

初回起動時は管理者アカウントを作成する必要があります。

#### 方法1: セットアップ画面から作成（推奨）
ブラウザで以下のURLにアクセス：
```
http://localhost:3000/setup.html
```
管理者IDとパスワードを入力して作成してください。

**注意**: このページは初回のみアクセス可能です。管理者アカウントが作成された後はアクセスできなくなります。

#### 方法2: APIエンドポイントから作成
curlコマンドで直接作成することも可能です：
```bash
curl -X POST http://localhost:3000/api/auth/admin/init \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"your-password"}'
```

**セキュリティ注意**:
- 本番環境では強固なパスワードを設定してください
- 管理者アカウントは1つのみ作成可能です
- 一度作成すると、上記の方法では追加作成できません

### ログイン
管理者アカウント作成後、ログイン画面から管理者としてログインできます。

### 基本的な運用フロー

1. **商品登録**
   - 「商品管理」タブから新規商品を登録
   - 商品名、カテゴリ、発注点、標準在庫数を設定

2. **初期在庫設定**
   - 商品管理画面の「初期在庫」ボタンから現在の在庫数を入力

3. **日々の運用**
   - 紙で在庫の減少を記録

4. **週次入力**
   - 「週次入力」タブから期間を設定
   - 各商品の出庫数（減少数）を入力して一括登録

5. **入庫処理**
   - 商品が入荷したら「入庫処理」タブから随時入力

6. **在庫確認**
   - ダッシュボードで発注が必要な商品を確認
   - 「発注依頼」タブで、依頼を出していてまだ届いていない商品を確認
   - CSVボタンでExcelファイルとして出力

### 履歴の修正
- 「履歴確認」タブから過去の入力を修正可能

### 履歴の絞り込みと CSV 出力
「履歴確認」タブで選んだ条件（カテゴリ・商品・期間）は、一覧にも「履歴CSV出力」にも
同じように効きます（サーバー側も一覧と CSV で同じ絞り込みの処理を使っています）。

- 期間は取引日で見ます（週次入力のように後日まとめて登録したものは、登録日ではなく取引日）
- 画面の一覧は新しい順に 50 件までですが、CSV は条件に合うものを全件出します
- CSV の「日時」は画面と同じく、取引日と登録した時刻（日本時間）です
- ファイル名で何を絞ったか分かるようにしています（例 `入出庫履歴_ニトリルグローブ(Ｍサイズ)_20250801-20260930.csv`）
- 「同じ商品・日付・担当者の履歴をまとめて表示」は画面の見せ方だけで、CSV は 1 件 1 行です
- 出庫で「出した人」が分かるものは、担当者の欄にその名前を出し、入力したアカウントが違えば
  「入力: ◯◯」と添えます。CSV には「出した人」の列があります

## 出庫記録（誰が何個出したか）

拠点のアカウントは店で共用しているので、ログインの名前だけでは誰が備品を出したのか
分かりません。出庫のたびに「出した人」を残します（`inventory_history.taken_by`）。

### 出庫のしかた

ダッシュボードの在庫カードの「-1」「-5」を押すと、すぐには減らさずにダイアログが開きます。

- **何個** — 押したボタンの数（1 か 5）が入っています。変えてかまいません
- **出した人** — 名前を入れるか、下に並ぶ名前を押します。名前は次の順に並びます
  1. 入場リンクで入ったときの名前（最初から入力欄にも入っています）
  2. ジョブカンの勤務予定で、今日この拠点に入っている人（始業の早い順）
  3. 最近 90 日に出庫で使われた名前（新しく使われた順）

前の人の名前は入れておきません。共用の端末で、次の人がそのまま押してしまうのを防ぐためです。
名前の空白（全角も）は 1 つにそろえるので、「田中　花子」と「田中 花子」は同じ人になります。
`< > " ' & \` などは使えません（入場リンクの操作者名と同じ決まり）。

「+1」「+5」はこれまで通りワンタップです（誤操作の修正用）。

**API では名前を省略できます。** 開いたままの古い画面（名前を送らない）から出庫できなく
なるのを避けるためです。省略すると入場リンクの名前を使い、それも無ければ空のまま残り、
出庫記録では「（未記入）」と出ます。この機能より前の出庫も「（未記入）」です。

**出した人は後から直せません。** 履歴の「修正」で直せるのは数量と備考だけです。
誰が出したかを後から書き換えられると、記録の意味がなくなるためです。

### 「出庫記録」タブ

期間（最初は直近 30 日）・カテゴリ・商品・出した人で絞って見られます。

- **補充が早すぎる商品** — 下の「補充が早すぎるとき」を参照
- **人ごとの集計** — 出した人ごとの回数・合計個数と、商品ごとの内訳
- **明細** — 新しい順に 100 件まで。全件は CSV で出せます

「出庫記録CSV出力」で、画面の条件に合う出庫を全件 CSV にします（Excel で開けます）。

| 列 | 中身 |
|---|---|
| ID・日時・商品名・カテゴリ・数量 | 履歴の CSV と同じ（日時は取引日と、登録した時刻（日本時間）） |
| 出した人 | 無ければ「（未記入）」 |
| 入力者 | 入力したアカウント（入場リンクで入ったときはその名前） |
| 備考 | |
| 補充が早い期間 | 補充が早すぎた区間に入る出庫だけ、その区間（例 `2025/02/12〜2025/02/17（5日で再補充・いつもは約14日）`） |

Excel で「補充が早い期間」の列を絞ると、早すぎた区間に誰が何個出したかが分かります。
ファイル名は `出庫記録_田中 花子_全商品_20250901-20250930.csv` のように、絞った条件が入ります。

### 補充が早すぎるとき

出庫の登録漏れや記録のない持ち出しがあると、記録とは関係なく棚から物が減るので、
補充の間隔が縮みます。前回補充した量が、いつもよりずっと早くなくなって、また補充した
商品を「出庫記録」タブの先頭に出します。

判定のしかた（`server/services/takeouts.js`）:

- **補充**は入庫のうち、「+1」「+5」ボタン（備考「クイック操作」）を除いたもの。
  同じ商品の同じ日の入庫は 1 回にまとめます
- 補充から次の補充までを 1 区間とし、「前回補充した量 ÷ 日数」をその区間の消費のペースとします
  （発注点で補充しているなら、区間のあいだに減るのはほぼ前回補充した量なので）
- 直前の区間（最大 6 個）のペースの中央値を「いつものペース」とし、そのペースなら
  もつはずの日数の**半分以下**で次の補充が来たら拾います
- いつものペースが分かるまで（区間が 2 つ以上たまるまで）は拾いません

日数ではなく量あたりで比べるのは、少しだけ補充したあとに早く次が来るのを拾わないためです。
拾った区間もいつものペースの計算に入れるので、消費が本当に増えたときは数回で追いつきます。

画面には、補充した日・前回からの日数・いつもなら何日もつか・その間に誰が何個出したかを出します。
「その間」は前回の補充日から今回の補充日まで（両端の日を含む）です。日付単位なので、
境目の日の出庫は前後どちらの区間にも数えます。

**記録のある出庫の合計が、前回補充した量よりずっと少ない**ときは、記録のない持ち出しや
登録漏れを疑ってください（画面の「出庫の記録は計 ◯個」）。

## 在庫計算のルール

在庫は 2 か所に保存されます。

- `products.current_stock` — 今の在庫数
- `inventory_history` — 増減の履歴

**この 2 つは常に一致します**（`current_stock` = 履歴の増減の合計）。ずれると、
どちらが正しいのか分からなくなり、発注や棚卸の判断が狂います。これを保つために、
在庫を動かす処理はすべて `server/utils/stock.js` の `applyStockChange()` を通し、
履歴の追記と在庫の更新を 1 つのトランザクションでまとめて行います。

新しく在庫を動かす処理を書くときは、この関数を使ってください。
`UPDATE products SET current_stock = ...` を直接書くと履歴が残らず、
上のルールが崩れます。

履歴の `quantity` の意味は種別ごとに違います。

| 種別 | 意味 |
|---|---|
| `in` | 入庫した数（正の数） |
| `out` | 出庫した数（正の数） |
| `adjust` | **増減量**（符号付き。棚卸調整・初期在庫・商品編集での在庫修正） |

### 過去データのズレを直す

在庫の更新と履歴の追記が別々のクエリだった頃のデータには、
上のルールが成り立たない商品があります（商品登録時の初期在庫が履歴に
残っていない、など）。次のスクリプトで調べて直せます。

```bash
# 調べるだけ（何も書き換えない）
node scripts/reconcile-stock.js

# 実際に調整履歴を入れる（先に必ずバックアップを取る）
node scripts/reconcile-stock.js --apply

# 拠点を指定する
node scripts/reconcile-stock.js --location 1
```

**現在庫は動かしません。** 店の人が毎日見て直してきたのは現在庫の方なので、
そちらを正として、差分を説明する調整履歴（備考「整合調整（過去の記録漏れ分）」）を
1 件ずつ足します。調整履歴は、在庫推移グラフの直近に不自然な段差が出ないよう、
その商品の最初の記録と同じ日付に置きます。何度実行しても重複しません。

## 発注依頼

在庫が発注点以下になると、自動で発注依頼ができます（入庫・出庫・週次入力のとき）。
画面から手で出すこともできます。

依頼の状況は 4 つです。

| 状況 | 意味 | どこで変わるか |
|---|---|---|
| 発注依頼中 (`pending`) | 依頼が出ていて、まだ発注していない | 自動発注・手で依頼 |
| 発注済 (`ordered`) | 発注した。届くのを待っている | 管理画面の「発注済み」 |
| 受領済 (`received`) | 届いた | 利用者画面の「入荷完了」 |
| キャンセル (`cancelled`) | 取りやめた | 利用者画面の「キャンセル」 |

**発注依頼中と発注済を「未入荷」と呼びます。** 未入荷の依頼がある商品には、自動でも
手でも、次の依頼を重ねて作りません。同じ商品が 2 行並ぶと、どちらで入荷完了すれば
よいか分からなくなるためです。

管理画面の「在庫状況（全店舗）」も未入荷をまとめて「依頼あり」として扱い、発注済に
した商品は「発注済」と出します（以前は依頼中しか見ておらず、発注済にすると
「発注必要」に戻って見えました）。

### 「発注依頼」タブ

未入荷の依頼を一覧で確認するところです。ダッシュボードの「発注依頼済み商品」欄は
依頼が 0 件だと消えてしまうので、いつでも開ける場所として別に置いています。

- **発注依頼済み商品** — 未入荷の依頼。状況・依頼日・現在庫・発注点・依頼者・備考と、
  「入荷完了」「キャンセル」のボタン。0 件なら「ありません」と出します
- **発注依頼が出ていない商品** — 在庫が発注点以下なのに、未入荷の依頼が無いもの。
  「発注依頼する」から依頼を出せます。無いときは欄ごと出しません

依頼が出ていない商品ができるのは、依頼をキャンセルしたとき、棚卸や商品の編集で
在庫が発注点を下回ったとき、最初から発注点以下で登録したときです。自動発注は
入庫・出庫のときにしか判定しないため、こうした商品は依頼が無いままになります。
この欄で拾います。

依頼日は日本時間の日付です（今年の分は「9/29」、それより前は年も出します）。

「発注依頼CSV出力」で、発注依頼済み商品の一覧を CSV で落とせます（Excel で開けます）。
列は画面と同じで、依頼日は「2026/09/29」の形、ファイル名は「発注依頼_20260929.csv」です。
商品名や備考は保存するときに HTML 用に変換しているので（「/」→「&#x2F;」など）、
CSV では元の文字に戻して出しています。

### 在庫カードの表示

在庫が発注点以下の商品のカードには、依頼の有無で違う札が出ます。

| 札 | 条件 |
|---|---|
| ⚠️ 発注依頼済み | 在庫が発注点以下で、未入荷の依頼がある |
| ⚠️ 発注依頼なし | 在庫が発注点以下なのに、未入荷の依頼が無い |
| ✓ 在庫十分 | 在庫が発注点より多い |

以前は在庫の数だけで「発注依頼済み」を出していたため、キャンセルした商品なども
依頼済みに見えていました。

## 在庫推移グラフ

商品ごとに、上下 2 枚のグラフを出します。

- **上: 在庫の推移** — 折れ線。発注点を破線で重ね、いつ下回ったかが分かる
- **下: 一日あたりの消費量** — 棒。期間平均を破線で重ねる

在庫（個）と消費（個/日）は意味の違う数字なので、1 枚に重ねて左右 2 本の
軸にすることはしていません。軸どうしの位置合わせは任意に決まってしまい、
実際にはない相関が見えてしまうためです。

グラフの下の「数字で見る」を開くと、同じ内容を表で確認できます。

### 記録漏れの断り

グラフは「今の在庫から履歴をさかのぼって過去を復元する」作りです。
そのため履歴に抜けがあると、過去の線が実際とずれます。

さかのぼった在庫がマイナスになる日があれば（実際にはありえない状態なので、
記録に抜けがある証拠です）、グラフの上に断りを出します。
その場合は `node scripts/reconcile-stock.js` で状況を確認してください。

## シフトの区切りごとの在庫確認

在庫の登録が 0 件のとき、「本当に何も動かなかった」のか「登録を忘れた」のかは
記録がないと区別できません。区切りごとに担当者が確認を残すことで、
この 2 つを分けられるようにしています。

- ダッシュボードの先頭に、その日の区切りが並びます
- 初期値は **朝（〜14:00）・昼（〜19:00）・晩（〜22:00）** の 3 つ
- その区切りで登録があれば「◯件で確定」、なければ「在庫の変化なし」を押します
- 区切りの時刻から **10 分の猶予**があり、そのあと締め切ります
  （朝番は 14:10、昼番は 19:10）。**その日の最後の区切り（晩番）は締め切りません**
- 締め切りまでに確認が済んでいないと、**締め切りと同時に LINE へ通知**が飛びます

### 猶予と締め切り

上がりの片付けを終えてから登録するので、区切りの時刻ちょうどで切ると、その区切り
ぶんの登録が次の区切りに落ちてしまいます。猶予の中の登録は、区切りの時刻を過ぎて
いても手前の区切りのものとして数えます。

| 区切り | 集計される時間帯 | 締め切り |
|---|---|---|
| 朝番 | 00:00〜14:10 | 14:10 |
| 昼番 | 14:10〜19:10 | 19:10 |
| 晩番 | 19:10〜24:00 | **なし** |

**締め切った区切りは確認できません。** 確定ボタンは消え、押しそびれた区切りは未確認
のまま残ります。後から取り繕えると、区切りごとに確認を残す意味がなくなるためです。
締め切りを過ぎてからの登録は、次の区切りのものとして数えます。

**その日の最後の区切りだけは締め切りません。** 締め切りは「その区切りぶんを次の
区切りに渡す」ための線なので、次が無いところに引く意味がありません。閉店の片付けを
終えてから登録することもあり、そこで締め切ると間に合わず、直しようもなく未確認だけが
残ります。日付が変われば、どのみち翌日の区切りに切り替わります。

判定は名前ではなく**並び順の最後**です（区切りは拠点ごとに変えられるため）。

猶予の長さは `SHIFT_GRACE_MINUTES` で変えられます。`0` にすると区切りの時刻
ちょうどで締め切ります。

「在庫の変化なし」を押すのが登録より楽だと、通知を消すためだけに押されるように
なります。それを避けるため、確認画面にはその区切りの登録件数を出し、0 件のときは
確認ダイアログを挟んでいます。管理のために `GET /api/shifts/history` で区切りごとの
「変化なし」の割合を確認できます。

### 区切りの設定

ダッシュボードの「区切りを変更」から、拠点ごとに変えられます
（API は `PUT /api/shifts/settings`）。

| 項目 | 内容 |
|---|---|
| `name` | 区切りの名前（例: 朝） |
| `end_time` | 区切りの時刻 `HH:MM` |
| `active_days` | 曜日ごとの有効/無効。日曜始まりの 7 文字（例 `1111100` は平日のみ） |

一覧から外した区切りは削除ではなく無効化されます。過去の確認記録を残すためです。

通知は締め切りと同時（点検の間隔ぶん、最大 1 分の遅れ）に飛びます。

### 注意: 定期処理が動く条件

未確認の通知は、サーバー内のタイマーで動いています。**Fly.io の
`auto_stop_machines` が有効でアクセスが途切れるとマシンが止まり、通知は飛びません。**
そのため `fly.toml` で `min_machines_running = 1` にしています。通知が不要なら
`0` に戻してかまいません（定期バックアップも同じ条件です）。

### 通知は今、止めてあります

**`NOTIFICATIONS_ENABLED` が未設定の間、通知は一切送りません。**
自動発注のお知らせも、シフト未確認の督促もです。通知を止めているときは、
未確認の見張り自体も動かしません。

送るように戻すとき:

```bash
flyctl secrets set NOTIFICATIONS_ENABLED=true
```

既定を「送らない」にしてあるのは、止めるからには理由があるからです。
設定を消し忘れただけで鳴り出す、ということが起きないようにしています。

**通知が止まっていても、画面の「在庫の変化なし」ボタンと確認の記録は
そのまま動きます。** 止めたのは知らせる部分だけです。

| 環境変数 | 既定 | 内容 |
|---|---|---|
| `NOTIFICATIONS_ENABLED` | （未設定＝送らない） | `true` で通知を送る |
| `SHIFT_MONITOR` | on | `off` で未確認の見張りを止める |
| `SHIFT_CHECK_INTERVAL_MINUTES` | 1 | 未確認を点検する間隔（分） |
| `SHIFT_GRACE_MINUTES` | 10 | 区切りの時刻から締め切りまでの猶予（分） |

## 別サイトからログインなしで入る

清掃管理表など、信頼している別サイトから、ログインを挟まずに入れます。
`LINK_SECRET` を両サイトに設定すると有効になります。未設定なら動きません。

判定は Referer ではありません。あれは送る側が自由に書ける値で偽装できます。
両サイトで共有した合言葉で作った署名を確かめています。

リンクは 5 分で切れ、1 回しか通りません。1 年の自動ログインは付けません。

手順とリンクの作り方は **ENTRY_LINK_SETUP.md** を見てください。

## ログイン状態の保ちかた

Fly.io はアクセスが途切れるとマシンを止めるため、サーバーの再起動は日常的に起きます。
そのたびに現場でログインし直すのは現実的でないので、2 段構えにしています。

1. **セッションを永続ディスクに保存**（`DB_DIR/sessions.db`）
   再起動してもセッションがそのまま残ります。CSRF のシークレットも一緒に残るので、
   画面を開いたままの端末が操作しても弾かれません。
2. **Remember Me トークンで復帰**（`remember_tokens`、1 年有効）
   セッションが失われた場合でも、Cookie のトークンからログイン状態を作り直します。
   `server/middleware/auth.js` の `attachRememberedSession` が全リクエストの前段で
   処理するので、管理画面の API も含めて効きます。

さらに画面側では、CSRF トークンが古くなって 403 が返ったとき、
取り直して 1 回だけ送り直します（`public/js/csrf.js`）。

この 3 つがそろっているので、`SESSION_SECRET` を変えてサーバーを入れ替えても、
利用者は操作を続けられます。

## マルチテナント機能

### 概要
マルチテナント機能を有効にすると、ユーザーごとに独立したデータベースが作成されます。
異なるユーザーでログインすると、それぞれ別のデータを管理できます。

### 有効化方法
`.env`ファイルに以下を追加：

```env
MULTI_TENANT=true
DB_DIR=/data  # データベースファイルの保存先
```

### 使い方
1. マルチテナントモードを有効化
2. アプリケーションを起動
3. 新規ユーザーを登録（`POST /api/auth/register`エンドポイント使用）
4. 各ユーザーでログインすると、専用のDBが使用される

## Fly.ioへのデプロイ

本システムは無料でFly.ioにデプロイできます。詳細は [DEPLOY.md](./DEPLOY.md) を参照してください。

### 簡易手順

```bash
# Fly.ioにログイン
flyctl auth login

# アプリケーションを作成

# ボリュームを作成（データ永続化）

flyctl secrets set MULTI_TENANT=true
flyctl secrets set DB_DIR=/data
flyctl secrets set SESSION_SECRET=your-secret-key

# デプロイ
flyctl deploy
```
